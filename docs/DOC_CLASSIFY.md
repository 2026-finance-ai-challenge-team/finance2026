# 문서 분류 모듈 설계

담당: 연우 · 작성 2026-08-18 · 대상 회의 `[260820] OCR 및 문서 분류 데모`

사용자가 아무렇게나 올린 파일 더미를 받아 **"이게 무슨 문서인가"**를 결정해
다음 단계로 넘기는 모듈의 설계다. 판정(다섯 상태)은 이 모듈의 일이 아니다.

---

## 0. 아키텍처 설계에서 제일 먼저 정하는 것

기능이 아니라 **경계**다. 모듈이 뭘 책임지고 뭘 책임지지 않는지를 먼저 못박고,
그다음 **인터페이스**(입력·출력)를 합의한다. 이 둘만 정해지면 4명이 서로를
기다리지 않고 동시에 작업할 수 있다. 순서를 반대로 하면 — 각자 만들고 나중에
합치면 — 반드시 안 맞는다.

이 문서의 §1(경계)과 §2(계약)이 그래서 제일 중요하다. §3 이후는 구현 방법이라
나중에 바꿔도 팀에 피해가 없다.

---

## 1. 경계 — 이 모듈이 하는 일과 안 하는 일

### 한다
- 파일의 실제 형식 판별 (확장자를 믿지 않는다)
- 페이지별 텍스트 확보 (내장 텍스트 우선, 없는 페이지만 OCR)
- **문서 유형 결정** + 신뢰도 + 그렇게 판단한 근거
- 분류에 필요한 **최소 필드**만 추출: 발급기관, 발급일, 문서번호
- 선택된 업무와의 **관련성 표시** (관련 / 불필요 / 판단 불가)

### 안 한다
- 다섯 상태 판정 (`준비 완료` 등) → 규칙 엔진
- 명의·주소·소득 등 **내용 필드** 추출 → 별도 추출 단계
- 사진 보정·품질 판정 → 비전 단계
- 문서 진위 확인 → 우리는 문서확인번호의 **존재**만 알리고, 확인은 공식 사이트로 안내

> **왜 내용 필드를 안 뽑나** — 분류는 "이게 주민등록등본인가"를 알면 끝난다.
> 그 사람이 누구인지는 알 필요가 없다. 개인정보 접촉면을 모듈 경계로 줄이는 게
> 이 설계의 핵심이고, 우리 팀이 "개인정보를 수집하지 않는다"고 말할 근거다.

## 2. 인터페이스 계약 — 08-20 회의에서 합의할 것

### 2-1. 입력

| 항목 | 내용 | 주는 사람 |
|---|---|---|
| `files[]` | 업로드된 원본 바이트 + 원본 파일명 | 영민 (파이프라인) |
| `task_id` | 선택된 업무 식별자 (예: `kakaobank.limit_release.living_expense`) | 영민 |
| `signatures[]` | 문서 시그니처 목록 (§2-3) | 찬형 (크롤링·DB) |

### 2-2. 출력 — JSON

```json
{
  "task_id": "kakaobank.limit_release.living_expense",
  "documents": [
    {
      "file_id": "f01",
      "source_name": "스캔_0001.pdf",
      "media": { "kind": "pdf", "pages": 2, "detected_by": "magic" },
      "text_source": [
        { "page": 1, "method": "embedded", "chars": 0 },
        { "page": 1, "method": "ocr", "chars": 812, "provider": "clova.general" }
      ],
      "classification": {
        "doc_type": "resident_registration_copy",
        "label_ko": "주민등록표 등본",
        "confidence": 0.94,
        "decided_by": "anchor",
        "evidence": [
          { "kind": "qr", "page": 1 },
          { "kind": "title_match", "pattern": "주민등록표\s*등본", "page": 1 },
          { "kind": "issuer_match", "value": "행정안전부", "page": 1 }
        ],
        "alternatives": [
          { "doc_type": "resident_registration_abstract", "confidence": 0.05 }
        ]
      },
      "fields": {
        "issuer":    { "value": "행정안전부", "confidence": 0.99 },
        "issued_at": { "value": "2026-08-11", "confidence": 0.91 },
        "doc_number_present": true
      },
      "relevance": { "status": "관련", "matched_rule": "required[2]" },
      "needs_user_confirm": false
    }
  ]
}
```

**규칙 3개**

1. `doc_type` 값은 **찬형 DB의 값을 그대로 쓴다.** 우리가 새로 짓지 않는다.
   양쪽이 각자 이름을 지으면 규칙 엔진과 조인이 안 된다. 통합 실패의 1번 원인이다.
2. 모든 분류에 `evidence` 가 붙는다. 근거 없는 분류는 출력하지 않는다.
3. 확신이 없으면 `doc_type: null` + `needs_user_confirm: true`. 추측으로 채우지 않는다.

### 2-3. 찬형에게 요청할 것 — 문서 시그니처

크롤링해서 DB에 넣을 한 건의 모양이다. **이게 나와야 우리 모듈이 동작한다.**

```json
{
  "doc_type": "resident_registration_copy",
  "label_ko": "주민등록표 등본",
  "issuer": "행정안전부",
  "issuer_aliases": ["정부24", "민원24"],
  "title_patterns": ["주민등록표\s*등본", "주민등록등본"],
  "required_anchors": ["세대주", "주민등록번호"],
  "negative_anchors": ["초본"],
  "doc_number_label": "문서확인번호",
  "issued_at_labels": ["발급일자", "발급일"],
  "validity_days": 90,
  "source_url": "https://www.gov.kr/...",
  "as_of": "2026-08-18",
  "last_checked": "2026-08-18"
}
```

- `negative_anchors` 가 핵심이다. 등본과 초본은 제목이 거의 같아서 **없어야 할 단어**로
  갈라야 한다. 이게 빠지면 등본/초본을 섞고, 규칙 엔진이 엉뚱한 판정을 낸다.
- `source_url` + `as_of` + `last_checked` 는 `AGENTS.md` §7의 필수 요건이다. 빠지면 안 된다.

## 3. 분류 캐스케이드 — 싼 신호부터

고도화는 큰 모델을 쓰는 게 아니라 **강한 신호를 먼저 쓰는 것**이다.
공문서는 서식이 고정이라, 아래 1~2단계에서 대부분 확정된다.

| 순위 | 신호 | 왜 강한가 | 비용 |
|---|---|---|---|
| 1 | **QR·바코드** | 전자증명서·정부24 발급물에 들어있고 발급기관·문서번호가 그대로 나온다. 오인식이 없다 | 0 |
| 2 | **문서확인번호 + 발급기관 문구** | 공문서 하단에 위치가 고정 | 0 |
| 3 | **제목 문자열 + 앵커** | 서식이 고정이라 정규식으로 충분 | 0 |
| 4 | **레이아웃 지문** | 글자가 뭉개져도 표·직인 위치는 남는다 | 낮음 |
| 5 | **AI 분류** | 위가 전부 실패한 비정형 사문서만 | 높음 |

```
0단계 · 형식 판별     magic bytes → pdf / image / 기타 (확장자 무시)
1단계 · 텍스트 확보   PDF 텍스트 레이어 있으면 pypdf, 없는 페이지만 OCR
2단계 · 신호 수집     QR → 문서번호 → 제목·앵커 (위 표 1~3)
3단계 · 시그니처 대조 찬형 DB와 매칭 → 점수·근거 산출
4단계 · AI 분류       2~3단계에서 확정 실패한 것만
5단계 · 관련성 판정   task 규칙과 대조 (§4)
```

각 단계는 **확정되면 즉시 멈춘다.** 1번에서 끝나면 OCR도, LLM도 호출하지 않는다.
비용과 정확도가 같이 좋아지는 방향이라 타협이 없다.

> 실측 근거 — 홈택스 발급 PDF는 텍스트 레이어가 1,583자로 OCR이 필요 없었고,
> 정부24 주민등록등본 PDF는 0자라 OCR이 필요했다. 파일 형식이 아니라
> **텍스트 레이어 유무**로 갈린다는 걸 실제 문서로 확인했다.

## 4. "관련 없는 문서" 처리 — 여기서 사고가 난다

**"모른다"와 "필요 없다"는 절대 같은 값으로 내보내지 않는다.**

| 상황 | 출력 | 사용자에게 |
|---|---|---|
| 분류됨 + 업무 규칙에 있음 | `관련` | 결과 목록에 표시 |
| 분류됨 + 업무 규칙에 없음 | `이번 업무에는 불필요` | "이건 이번엔 안 챙겨도 돼요" |
| 분류 실패 | `판단 불가` + `needs_user_confirm` | "이 문서가 뭔지 확인해 주세요" |

분류 실패를 `불필요`로 처리하면, 실제로는 필수인 서류가 조용히 빠진 채
`준비 완료`가 나온다. `CLAUDE.md`가 가장 위험하다고 한 **거짓 준비 완료**의 전형적인 경로다.
모르는 건 모른다고 내보내야 한다.

## 5. JSON인가 CSV인가

**모듈 출력은 JSON.** 문서 하나가 페이지 배열 + 근거 배열 + 후보 배열을 갖는
중첩 구조라 CSV로는 표현이 안 된다.

**CSV는 정답표에만 쓴다.** 찬우의 검증용이고, 한 줄이 한 문서라 사람이 엑셀로 채점할 수 있다.

```csv
file,expected_doc_type,expected_relevance
등본_정상.pdf,resident_registration_copy,관련
초본_함정.pdf,resident_registration_abstract,관련
취업후기.pdf,,이번 업무에는 불필요
흐린사진.jpg,,판단 불가
```

## 6. 개인정보 — 분류는 내용을 알 필요가 없다

- 출력 JSON에 **원문 텍스트를 담지 않는다.** 매칭에 쓴 패턴과 위치만 남긴다.
- 5단계 AI 분류로 외부에 보낼 때는 **마스킹 후 문서 상단 영역만** 보낸다.
  제목·발급기관은 대부분 상단에 있어서 그걸로 충분하다. 보내는 양이 줄어
  비용과 지연도 같이 준다.
- 로그에 남기는 건 `file_id`, `doc_type`, `confidence`, 처리 시간까지다.
  주민번호·계좌번호·인증정보는 어떤 경로로도 로그에 넣지 않는다.
- 테스트·샘플은 합성 데이터만 쓴다. 실제 개인문서는 저장소에 넣지 않는다.

---

## 7. 검증 — 무엇을 채점할 것인가

전체 정확도는 지표로 쓰지 않는다. 아래 둘이 우선이다.

| 지표 | 통과선 |
|---|---|
| 분류 실패를 `불필요`로 잘못 내보낸 건수 | **0건** |
| 등본/초본처럼 헷갈리는 쌍의 혼동 | 0건 |
| 분류 정확도 (확정된 것 중) | 측정만, 목표치 나중에 |

찬우의 합성 세트 + 위 CSV 정답표로 회귀 검증한다. 시그니처를 고칠 때마다 돌린다.
