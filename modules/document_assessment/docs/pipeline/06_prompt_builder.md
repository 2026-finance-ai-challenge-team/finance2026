# 설명 프롬프트 빌더

## 목표

결정론적으로 생성된 `Assessment` 결과를 설명용 LLM에 전달할 수 있는 안전하고 구조화된 프롬프트로 변환한다.

LLM은 결과를 설명하는 역할만 수행한다.

LLM은 은행 업무상의 판정을 내리지 않는다.

---

# 입력

```text
Assessment
```

---

# 출력

구조화된 프롬프트 payload.

예:

```json
{
  "task": "explain_document_assessment",

  "language": "ko",

  "constraints": [
    "어떠한 규칙 상태도 변경하지 않는다.",
    "추가적인 은행 업무 요구사항을 임의로 생성하지 않는다.",
    "제공된 심사 결과만 설명한다.",
    "UNKNOWN을 거절로 설명하지 않는다.",
    "필요한 다음 조치를 명확하게 설명한다."
  ],

  "assessment": {
    ...
  }
}
```

---

# 필수 동작

## READY

문서 심사 파이프라인에서 모든 blocking 요구사항이 충족된 것으로 판정되었음을 설명한다.

---

## ACTION_REQUIRED

어떤 요구사항이 명확하게 `UNSATISFIED`인지 설명하고, 어떤 근거가 누락되었거나 서로 충돌하는지 설명한다.

---

## REVIEW_REQUIRED

현재 사용 가능한 정보만으로는 판정을 내리기에 충분하지 않음을 설명하고, 구체적으로 어떤 근거가 아직 확인되지 않았는지 명시한다.

---

# 개인정보 보호 경계

프롬프트 입력에는 불필요한 민감정보가 포함되어서는 안 된다.

프롬프트 빌더는 이미 마스킹되었거나 비식별화(sanitized)된 구조를 입력으로 받을 수 있어야 한다.

---

# 중요 언어 규칙

설명에서는 다음과 같은 내용을 주장해서는 안 된다.

- 은행의 최종 승인
- 규제 또는 컴플라이언스상의 최종 승인
- 계좌 개설의 성공 또는 완료

다음과 같은 표현을 우선적으로 사용한다.

```text
"현재 제출된 서류 기준"

"PoC 검증 결과"

"추가 확인 필요"
```

---

# 승인 기준

- `Assessment`의 상태 값은 정확하게 보존되어야 한다.
- `UNSATISFIED`와 `UNKNOWN`은 서로 다른 의미로 설명되어야 한다.
- 새로운 규칙을 임의로 추가해서는 안 된다.
- 불필요한 민감 필드는 제외되어야 한다.
- 프롬프트는 JSON으로 직렬화할 수 있어야 한다.
