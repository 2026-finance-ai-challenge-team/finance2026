# doc_classify — 문서 분류 모듈

담당: 연우 · 설계 근거: [`docs/DOC_CLASSIFY.md`](../../docs/DOC_CLASSIFY.md)

사용자가 올린 파일이 **무슨 문서인지** 결정해 다음 단계로 넘긴다.
다섯 상태 판정(`준비 완료` 등)은 하지 않는다. 규칙 엔진의 몫이다.

## 실행

저장소 루트에서 실행한다.

```bash
# 자체 검증 — 합성 데이터만 쓰고 API를 호출하지 않는다
python modules/doc_classify/test_doc_classify.py

# 분류 실행 (폴더를 주면 지원 확장자를 모두 처리)
python -m modules.doc_classify.cli <파일_또는_폴더>

# API 호출 없이 (텍스트 레이어 있는 PDF만 처리됨)
python -m modules.doc_classify.cli <경로> --no-ocr

# 한 장짜리 요약 출력 + 제출 묶음 생성
python -m modules.doc_classify.cli <경로> --report --pack out/제출묶음

# 결과 JSON 저장
python -m modules.doc_classify.cli <경로> --json out.json
```

## OCR 호출을 아끼는 구조

CLOVA 무료 한도가 **월 100건**이라 호출 수가 곧 예산이다. 그래서 2단으로 돈다.

```
1차   pypdf로 내장 텍스트만 읽는다              API 0회
      → 여기서 분류가 확정되면 끝. OCR 안 부른다
2차   확정 못 했고 빈 페이지가 남았을 때만 OCR   파일당 최대 1회
```

여러 쪽짜리 PDF도 통째로 한 번만 보낸다(CLOVA가 `images[]`로 페이지별 결과를 준다).
실측: 문서 3건 중 텍스트 PDF 1건은 건너뛰어 **OCR 2회**로 끝났다.
`--no-ocr`을 쓰면 호출이 0회다.

`.env`에 `NCP_OCR_INVOKE_URL`, `NCP_OCR_SECRET_KEY`가 있어야 OCR 경로가 동작한다.
발급 방법은 루트 `README.md`의 **API 키 발급 방법** 토글에 있다.

## 구성

| 파일 | 단계 | 하는 일 |
|---|---|---|
| `extract.py` | 0~1 | magic bytes로 형식 판별 → PDF는 내장 텍스트 우선, 텍스트 없는 페이지만 OCR → **글자 크기로 제목 검출** |
| `classify.py` | 2~3, 5 | 신호 수집 → 시그니처 대조 → 유효기간 계산 → 업무 관련성 판정 |
| `pack.py` | 출력 | 한 장짜리 요약 + 파일명 정규화 복사본 + 체크리스트 + ZIP |
| `cli.py` | — | 실행 진입점 |
| `signatures/*.json` | — | 문서 서식 시그니처. **찬형 DB 연동 전 임시값** |
| `tasks/*.json` | — | 업무별 필요 서류. **임시값** |

공개 API는 `classify_files(paths, task_id)` 하나다.

## 요약과 패킹

`--pack`은 아래를 만든다. **원본은 절대 수정하지 않는다.**

```
제출묶음/
├─ index.md       한 장짜리 요약 — 무슨 문서가 있고, 유효기간은 언제까지고, 뭐가 더 필요한지
├─ checklist.md   제출 체크리스트
├─ 원본/          업로드한 파일 그대로
└─ 제출용/        이름만 규칙에 맞게 바꾼 복사본
제출묶음.zip
```

파일명 규칙은 `발급일_문서종류_연번.확장자`다. 파일을 열지 않아도 무슨 문서인지 보이게 하는 게 목적이다.

```
류연우_주민등록등본.pdf            ->  2025-09-09_주민등록표등본_01.pdf
국민은행 통장사본.jpg              ->  2019-06-24_통장사본_03.jpg
IMG_2931.jpg (분류 실패)           ->  확인필요_IMG_2931_07.jpg
```

### 발급일과 유효기간

발급일은 두 가지로 뽑는다.

1. `발급일자` 같은 **라벨 바로 뒤의 날짜** → 확실한 값
2. 라벨이 없으면 문서에서 **가장 늦은 날짜**를 추정값으로 (주민등록등본이 이렇다)

추정값일 때는 **"유효함"을 단정하지 않는다.** 만료 쪽으로 틀리는 건 안전하지만,
유효 쪽으로 틀리면 거짓 준비 완료가 되기 때문이다.

| 발급일 | 만료됨 | 유효함 |
|---|---|---|
| 확실 | `기한 만료` | `83일 남음` |
| 추정 | `기한이 지났을 수 있음 — 발급일 확인 필요` | `83일 남음(추정) — 발급일 확인 필요` |

## 지금 상태에서 믿어도 되는 것과 아닌 것

**믿어도 되는 것**

- 형식 판별과 페이지별 텍스트 확보 (실제 문서 9건으로 확인)
- 헷갈리는 쌍의 분리 — 등본/초본, 종합소득세/개인지방소득세/접수증
- 분류 실패를 `이번 업무에는 불필요`로 넘기지 않는 것

**믿으면 안 되는 것**

- `signatures/`와 `tasks/`의 내용. 전부 `"verified": false`이고 공식 출처가 없다.
  **이 값으로 사용자에게 준비 완료를 말하면 안 된다.** 찬형 조사 결과로 교체한다.
- 사문서(재직증명서 등) 분류. 서식이 제각각이라 현재 패턴으로는 잘 안 잡힌다.

## 아직 안 만든 것

- **QR·바코드 판독** — 설계상 1순위 신호인데 빠져 있다. 정부24 발급물의 QR을 읽으면
  분류가 확정되고 OCR도 필요 없다. 의존성(`opencv-python` 또는 `pyzbar`)이 필요해서
  실제 표본에 QR이 있는지 확인한 뒤 넣는다.
- **AI 분류 (4단계)** — 1~3순위 신호로 얼마나 걷히는지 보고 결정한다.
- **레이아웃 지문** — 같은 이유로 보류.

## 제목은 글자 크기로 찾는다

문서 제목은 본문보다 크게 인쇄된다. OCR이 필드마다 주는 좌표에서 **글자 높이**를 재면
제목을 직접 집어낼 수 있다. 실측(정부24 주민등록표, 필드 318개):

```
중앙값 21px · 제목 33~40px(1.6~1.9배) · 위치 상단 8~12%
하단 발급기관 직인도 39px    ← 크기만으로는 제목과 구분이 안 된다
```

그래서 조건이 둘이다 — **중앙값의 1.5배 이상**이고 **페이지 상단 30% 안**.

CLOVA는 자간이 넓은 큰 제목을 낱자로 쪼개 준다(`주 민 등 록 표 ( 초 본 )`).
좌표로 줄을 다시 세우고, 대조할 때는 공백을 지운 형태로도 검사한다.

이 방식으로 정부24 문서가 `판단 불가(0.40)` → `주민등록표 초본(0.80)`으로 바뀌었다.
파일명은 `등본(초본)`이었지만 실제 제목은 초본이다. **파일명으로 판정하지 않는** 이유다.

## 알려진 한계

- **필드가 적은 문서에서 제목 검출이 무너진다.** 신분증·짧은 영수증처럼 글자가 적으면
  제목 글자가 중앙값을 지배해 아무것도 안 잡힌다. 이때는 상단 500자 근사로 넘어간다.
- 텍스트 PDF는 글자 크기 정보가 없어 상단 500자 근사를 쓴다. `pypdf`의 `visitor_text`로
  폰트 크기를 받을 수 있으니, 텍스트 PDF 오분류가 실제로 나오면 그때 넣는다.
- `negative_anchors`는 문서 전체에서 찾는다. 안내문에 다른 서류 이름이 있으면
  정상 문서가 탈락할 수 있다. 탈락은 `판단 불가`로 이어지므로 오분류보다는 안전한 실패다.
- `MIN_CHARS_PER_PAGE = 30` — 이 값 미만인 페이지를 OCR로 넘긴다. 실제 표본으로 조정해야 한다.
